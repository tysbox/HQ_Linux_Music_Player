# V3.0 Phase 0-4 最終点検記録

> ## ⚠️ 2026-10-02 訂正 — 本書の「OSリブート後の自動起動」記述は不正確
>
> 本書は「OSリブート後も全サービスが `enabled` かつ `active` で、3003・8002・
> 6600・1234 が LISTEN、`/health` が `dsp: connected` となった」と記載していたが、
> 2026-10-02 の再点検で **CamillaDSP については再現しない** ことを確認した。
>
> **原因**: `camilladsp.service` は `HQ_DSP_YAML=/tmp/camilladsp/active_dsp.yml` を
> 参照していたが、`/tmp` は **tmpfs** でありリブートで必ず消去される。
> unit の `ExecStartPre` は `mkdir -p` のみで YAML を生成せず、生成処理は
> API 呼び出し時のみ走るため、**自動起動の経路がibe pensé存在しなかった**。
>
> **証拠**（journalctl、全 4 boot 分の集計）:
>
> | boot | 起動時刻 | "Could not open config file" | listen 成功 |
> |---|---|---|---|
> | -3 | 2026-09-25 16:18 | 2,493 | 0 |
> | -2 | 2026-09-25 21:07 | 69 | 0 |
> | -1 | 2026-10-01 03:16 | 1,959 | 0 |
> | 0 | 2026-10-02 00:21 | 922 | 0 |
>
> listen 成功は一度も 0 になっておらず、CamillaDSP は過去 4 回の起動すべてで
> ポート 1234 を開いていない。本書が記録した 9/25 の復旧は、boot 開始 2 分後の
> **手動配置 + `systemctl restart`** によるものであり、自動起動の証拠ではない。
>
> **的措施**: 設定/状態の配置先を `/var/lib/camilladsp` (永続) へ移行。
> 適用スクリプトとロールバック: `.safety_backups/dsp-persist-20261002-010006/`
> ガード: `tests/unit/test_dsp_paths_consistency.py`
