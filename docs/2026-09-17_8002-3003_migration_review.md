### A-3. systemd の `Conflicts=` が 3002 と 3003 を排他にしている

`/etc/systemd/system/unified-shell.service`:

```ini
Conflicts=audiophile-backend.service audiophile-frontend.service hq-dmp-backend.service hq-dmp-frontend.service
Conflicts=audiophile-new-gui.service
```

**重要**: systemd の `Conflicts=` は**双方向**に作用する。したがって `unified-shell.service` と `audiophile-new-gui.service` は**同時起動できない**。

**影響**: 「移行」の意図がどちらかで対応が変わる。

| 意図 | 必要な対応 |
|---|---|
| 3002 を 3003 で**置換**（推奨） | `systemctl disable --now unified-shell.service` で旧を退役。`Conflicts=` はそのままで問題なし |
| 3002 と 3003 を**併設** | `unified-shell.service` から `Conflicts=audiophile-new-gui.service` 行を削除 |

**備考**: 逆に `new-gui/audiophile-new-gui.service` 側には `Conflicts=` が一切無い。既存の旧 DSP/DMP サービス（`audiophile-backend.service` 等）との排他が設定されていない点も非対称。

## B. 構造・保守性の問題（再発リスク）

### B-1. `NEXT_PUBLIC_API_URL` は実効性が無い（設計上の落とし穴）

`/etc/systemd/system/unified-shell.service`:

```ini
Environment=NEXT_PUBLIC_API_URL=http://localhost:8002
```

Next.js の `NEXT_PUBLIC_*` は**ビルド時にクライアントバンドルへインライン化**される。したがって:

- **サービス起動時（実行時）の環境変数は、既存ビルドには一切効かない**（デッド設定）
- 実際に動いているのは `src/lib/api.ts` のフォールバック式の方

```ts
// unified-shell/src/lib/api.ts / new-gui/src/lib/api.ts（同一内容）
const DEFAULT_API_URL =
  process.env.NEXT_PUBLIC_API_URL ||
  (typeof window !== 'undefined'
    ? `${window.location.protocol}//${window.location.hostname}:8002`
    : 'http://localhost:8002')
```

**影響**: バックエンド 8002 据え置きなら**機能的には問題なし**。ただし「env で切り替えている」という誤解が、将来のポート変更時に事故の温床になる。

**対応**: コメントで明示するか、`next.config.ts` の `env` でビルド時に注入する方式へ統一。

## G. 追記（2026-09-17 18:10）— 並列運用の可否についての回答

### 質問

> 現在は、両者を並列で使用して、8003 の機能と動作の確認が取れた時点で移行予定です。
> 一部の不具合を調整し、点検を進めながら移行すれば大きな問題はないという理解でよろしいでしょうか？

### 短い回答

方針（8002 据え置き＋3002→3003 へ段階移行、コードの大改修不要）は正しい。
ただし **「いまのまま両者を並列で使用」はできない**。実機の systemd 設定上、
`unified-shell.service`（3002）と `audiophile-new-gui.service`（3003）は
**同時起動できない排他関係**にある。並列確認をしたい場合は、
下記の最小 3 点の調整が先に必要である。

> ※「8003」は「3003」のこととして読んだ（バックエンド 8002 / フロント 3003）。

### G-1. なぜ並列できないのか（実機で確認済み）

1. `/etc/systemd/system/unified-shell.service` に
   `Conflicts=audiophile-new-gui.service` がある（2 行目）。
2. systemd の `Conflicts=` は**双方向**に作用する。
   `systemctl show` の実効値でも両者に相手が入っていることを確認済み:
   - `audiophile-new-gui.service: Conflicts=unified-shell.service`
   - `unified-shell.service: Conflicts=audiophile-new-gui.service`
3. この状態で `systemctl start audiophile-new-gui.service` を実行すると、
   稼働中の `unified-shell.service`（3002）が**自動停止**させられる。
   逆も同じ。ログ上は `Stopping unified-shell.service...` のように出て、
   「アプリの不具合」に見えるが原因は systemd の排他である。

現在の実機状態（2026-09-17 確認）:

```
hq-api.service              active   （8002 LISTEN 中）
unified-shell.service       active   （3002 LISTEN 中）
audiophile-new-gui.service  inactive （3003 未 LISTEN）
```

つまり「3003 の動作確認」は現状 start した瞬間に 3002 が落ちる。

### G-2. 並列確認のために先に必要な最小調整（3 点）

並列確認期間だけ、以下の暫定対応を行う:

| # | 対応 | 理由 |
|---|---|---|
| 1 | `/etc/systemd/system/unified-shell.service` から `Conflicts=audiophile-new-gui.service` の 1 行を削除し `sudo systemctl daemon-reload` | 双方向排他を解消。ポート 3002/3003 は別なので共存可能。バックエンド 8002 は共有で問題なし（読み取り中心の確認なら競合しない） |
| 2 | `systemctl daemon-reload` を必ず実行 | 現在 `audiophile-new-gui.service changed on disk` 警告が出ており、ロード済みユニットが古い。これを放置すると編集が反映されない |
| 3 | `scripts/monitor_services.sh` を並列期間中は停止または対象変更 | 現スクリプトは `unified-shell.service` が落ちると自動 restart する。確認作業と干渉するため、移行完了まで cron を止めるか、対象に `audiophile-new-gui.service` を追加する |

> 旧 DSP/DMP 系（audiophile-backend 等）との `Conflicts=` は残してよい。
> 外すのは new-gui との 1 行のみ。

### G-3. 並列確認中の注意（大きな問題にしないための約束）

- **DSP の書き込み系は片方からだけ操作する**: `/api/apply`, `/api/dsp_update`,

- **ヘルスゲート無しを意識する**: new-gui 側は 8002 未起動でも起動してしまう。
  並列確認中は先に `curl -sf http://localhost:8002/health` を通してから

このとき外した `Conflicts=` を戻す必要はない（退役後は排他不要）。
`monitor_services.sh` の監視対象を `audiophile-new-gui.service` に切り替え、
`HANDOVER.md` 等のポート表を 3003 に更新して完了。

### G-5. 結論

- 「点検しながら移行すれば大きな問題はない」という理解は**方向として正しい**。
- ただし現状のままでは **3002 と 3003 の並列起動そのものが systemd に止められる**
  ため、「両者を並列で使用して確認」は**あと一手（G-2 の 3 点）が必要**。
- その一手を済ませれば、アプリコード側（8002 参照・CORS・WS）は
  既に 3003 対応済みのため、段階移行は可能である。

*本レポートは修正・実装を行わず、現状の構造と問題点を整理したものです。*

### 短い回答

- アプリコード側（8002参照・CORS・WS）は既に3003対応済みのため、コードの大改修は不要

ただし **現状のままでは「デフォルト3003」にならない**。実機確認（2026-09-18）では
3サービスとも `enabled` だが、起動中は `hq-api` と `unified-shell` のみで
`audiophile-new-gui` は `inactive`、LISTENも `8002` と `3002` のみだった。
これは `Conflicts=` の相互排他により3002が3003を止めている（またはその逆の順序で潰し合う）ためである。

### H-1. 現状確認（2026-09-18 実機）

```
enabled: hq-api / unified-shell / audiophile-new-gui（3つとも enabled）
active:  hq-api(active) / unified-shell(active) / audiophile-new-gui(inactive)
LISTEN:  0.0.0.0:8002 / 0.0.0.0:3002（3003なし）
```

- 3つとも `enabled` ＝ ブート時に3つとも起動しようとする
- ところが `unified-shell` と `audiophile-new-gui` は `Conflicts=` で相互排他
  （`systemctl show` の実効値で両方向を確認済み）のため、**ブートのたびにどちらかが潰される**
- 現在はたまたま3002側が生き残っている状態。これではリファイン開発のたびに
  「3003を start したら3002が落ちた／その逆」が起き、比較作業にならない

補足：定期監視の干渉はなし。`crontab -l` は空、`*.timer` なし、
`scripts/monitor_services.sh` は手動実行のみ。ただし将来 cron 化する場合は
対象を `audiophile-new-gui.service` に変える必要がある（現状は旧名のまま）。

### H-2. 切り替え手順（デフォルト3003＋3002オンデマンド）

**一度だけ実行する切替作業：**

```bash
# 1) 3002をブート対象から外す（ファイルは残るので手動起動は可能）
sudo systemctl disable unified-shell.service

# 2) daemon-reload（unit変更の警告が出ていた場合の保険）
sudo systemctl daemon-reload

# 3) 3002を止めて3003を起動（Conflicts=のため stop→start の順）
sudo systemctl stop unified-shell.service
sudo systemctl start audiophile-new-gui.service

# 4) 確認
systemctl is-active hq-api.service audiophile-new-gui.service
curl -sf http://localhost:8002/health
curl -sI http://localhost:3003/
ss -ltn | grep -E ':8002|:3003'
```

以後、ブート時は `8002＋3003` だけが上がる。

**比較のため一時的に3002に戻す手順：**

```bash
# 3003→3002（Conflicts=のため stop→start の順を守る）
sudo systemctl stop audiophile-new-gui.service
sudo systemctl start unified-shell.service
curl -sI http://localhost:3002/

# 3002→3003（戻す）
sudo systemctl stop unified-shell.service
sudo systemctl start audiophile-new-gui.service
curl -sI http://localhost:3003/
```

> 注意：`start` だけ叩いて「並列で両方」はできない。
> `Conflicts=` が双方向のため、起動した側が相手を自動停止させる。
> 必ず **stop→start の順**で切り替えること。
> ログに `Stopping ...` と出ても故障ではない。
