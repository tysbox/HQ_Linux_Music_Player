## 2. 希望する3項目の実現性

### 2.1 クロスフィード／クロストークキャンセルの角度×距離

この2つは、用途と処理を分けたほうがよい。

#### A. ヘッドホン用クロスフィード：比較的取り組みやすい

左右が完全分離したヘッドホン再生に、スピーカー聴取に似た反対耳への音の回り込みを加える。

既存の Mixer に次を組み合わせることで実装できる。

- 反対チャンネルへ送る信号の減衰
- サブミリ秒程度の遅延
- 頭による遮蔽を近似する、周波数依存の減衰

**左右に極端に振られた録音の聴きやすさ改善**などに向いている。ただし、本格的な頭外定位まで保証するものではない。

角度調節は可能だが、まず「正面から左右それぞれ何度か」を明確に定義する必要がある。左右各30°と、左右の開き角30°は別である。

**距離については、現在の計算方法をそのまま使うことは勧めない。**

現在のコードには、距離に応じて約1.5～58msの遅延を返す処理がある。しかし、次は別の量である。

- 音源から頭までの到達時間
- 左右の耳への到達時間差

前者をそのままクロスフィードの遅延にすると、遠方のスピーカー感ではなく、エコーや音色変化になりやすい。

おすすめの分担は次のとおり。

> **角度:** 耳間の遅延・遮蔽特性を調節する。  
> **距離感:** 直接音と初期反射・残響の比率を中心に調節する。

初期版では「距離○mの厳密再現」より、「Near／Mid／Far」の聴感プリセットとして始めるほうが堅実である。

#### B. スピーカー用クロストークキャンセル：本格版は難しい

スピーカーから反対側の耳へ届く音を打ち消す処理である。

**単に反対チャンネルを逆位相で混ぜれば完成、というものではない。** 左右のスピーカーから左右の耳への4経路を考慮し、周波数ごとの振幅・位相を補償する必要がある。

難しい点は次のとおり。

- 頭の位置が動くと打ち消し条件が変わる。
- 部屋の反射の影響を受ける。
- 強い逆補正は大きなゲイン増加を招く。
- 高域ほど位置ずれに敏感になる。

CamillaDSP の Mixer と複数の畳み込みフィルターで実行する構成は可能だが、**難所はエンジンではなく、補正フィルターの設計と検証**である。

まずは「中央の固定リスニング位置向け・帯域限定・補正量制限付き」の実験機能が妥当。ヘッドホン用クロスフィードとは別モードにすることを勧める。

### 2.2 ヘッドホンキャリブレーション：最もおすすめ

**機種別の周波数特性補正であれば、比較的容易で、効果も期待しやすい項目である。**

現在の EQ 機構を拡張して、以下を持たせれば実現できる。

- メーカー・機種別の補正プロファイル
- 複数バンドのパラメトリック EQ（PEQ）
- 補正に必要なプリアンプ減衰
- 目標音色の選択
- 補正の有効／無効と比較機能

既存の `planar-magnetic` などは一般的な音色プリセットであり、**特定機種の測定特性を反転補正するものではない。** 「音色プリセット」と「機種補正」は別枠にすると分かりやすい。

最初は、利用条件と測定条件が確認できる既存プロファイルを少数取り込み、PEQ として適用する方式がよい。大量の機種データベース対応は後からでも可能である。

ただし、公開測定ベースの補正には限界がある。

- 個体差、イヤーパッドの状態、装着・密閉状態の違い
- 測定器や目標カーブの違い
- 高域の個人差

したがって、**「その人の耳元を完全に校正する機能」ではなく、「機種特性を目標カーブに近づける機能」**として提供するのが適切である。

### 2.3 スタジオ／ホールの模倣：既存機能から発展させやすい

厳密にはルームキャリブレーションではなく、**ルームシミュレーション／仮想音響空間**である。

現在すでに IR リバーブがあるため、基本的な空間演出は拡張しやすい。

| 段階 | 内容 | 難易度 |
|---|---|---|
| 第1段階 | スタジオ、小ホール、大ホールなどのプリセットと残響量調節 | 低～中 |
| 第2段階 | 初期反射、残響時間、残響の明るさ、距離感を調節 | 中 |
| 第3段階 | ヘッドホンで仮想スピーカーと室内音場を再現 | 中～高 |

実測 IR を使わず、**初期反射と残響をモデルから合成した IR を、準備段階で生成して畳み込む方式**も可能。既存の再生系を大きく変更せず導入できる。

一方、現在のコードは WET の左右へ同じ Conv 定義を適用しており、左右別応答や L→R／R→L の交差応答を明示的に扱う構造ではない。本格的な空間再現には、ここを拡張する必要がある。

音楽には元から録音会場の残響が含まれる。ホール効果を強く足すと明瞭度が落ちるため、**最初は短いスタジオ的な初期反射を少量加える方向**がおすすめである。

スピーカー再生では実際の部屋の響きも加わるので、自宅を別のホールに置き換えるような再現はできない。

## 3. 追加するなら、費用対効果の高い機能

| 機能 | おすすめ理由 | 難易度 |
|---|---|---|
| **低音・高音シェルフ／ティルト EQ** | 録音ごとの「明るすぎる・重すぎる」を少ない操作で調整できる | 低 |
| **左右バランス・左右独立 EQ** | 左右の機器差や設置の非対称への手動調整に便利 | 低～中 |
| **小音量向けラウドネス補正** | 夜間など、小音量で低音の量感が不足する場面に有用 | 中 |
| **ReplayGain の操作・表示** | 対応タグがあれば、曲やアルバム間の音量差を抑えられる | 低～中 |
| **音量をそろえた A/B 比較** | 「大きくなったから良く聞こえる」を避け、効果を判断しやすい | 中 |
| **控えめなステレオ幅調整** | 広すぎる録音を狭めるなど、聴き疲れ対策に使える | 低 |

既存の「Loudness」は固定 EQ である。再生音量に連動するラウドネス補正とは区別したほうがよい。ただし、実際の音圧は DSP の音量値だけでは分からないため、基準音量をユーザーが調節できる設計が必要になる。

優先度としては、**ヘッドホン機種補正 → 軽いクロスフィード → ティルト EQ／小音量補正**を推奨する。

## 4. 構造改革は必要か

**全面刷新は不要だが、機能を増やす前に DSP の責務を整理する価値は高い。**

以下は今後の設計提案であり、実装済みの構造を示すものではない。

### 4.1 「出力先」と「聴取方式」を分ける

USB DAC はヘッドホンにもスピーカーにも使える。デバイス名だけで処理を判断せず、次を独立して持たせる。

- 出力デバイス
- ヘッドホン／スピーカー
- 機種補正プロファイル
- 空間処理モード

これにより、クロスフィードとクロストークキャンセルの誤適用を防げる。

### 4.2 音色・空間・機器補正を別の処理段にする

概念上は次の整理が適している。

```text
入力
 → 入力ゲイン／ヘッドルーム
 → 好みの音色調整
 → 空間処理
 → 出力機器補正
 → 最終音量・出力監視
```

空間処理内部で原音と残響を分岐・合流させる。

現在は EQ が DRY 側にだけ入るため、その場所へヘッドホン補正を追加すると、**残響側には機種補正がかからない**構造になる。機器補正は、原則として合流後の出力全体へ適用する設計がよい。

### 4.3 DSP 更新経路と設定定義を一本化する

現在は API 側と DSP モジュール側に更新処理が重複し、内容にも差がある。

また、実際の API ではリロードに失敗しても設定を保存し、成功レスポンスを返す経路がある。機能が増える前に、次の流れへ整理したい。

1. 設定を検証する。
2. 候補の DSP 構成を生成する。
3. CamillaDSP で受理されたことを確認する。
4. 適用済み設定として保存・通知する。
5. 失敗時は直前の正常設定を維持する。

GUI にも「選択した設定」と「実際に適用できた設定」の違いが分かる表示を持たせる。

### 4.4 ゲイン管理と IR 管理を共通基盤にする

現在の固定的な −3dB／−4dB のヘッドルームでは、EQ・左右混合・残響を重ねた全条件でのクリッピング防止は保証できない。

必要なのは次の項目である。

- 補正量に応じたプリアンプ
- フィルター／混合を含めたゲイン確認
- クリッピング監視
- IR のレート・チャンネル・長さ・ゲイン・出典管理

現状は192kHz固定、チャンクサイズ16384で、1チャンクは約85msである。これは総遅延そのものではないが、長い IR を増やす際の負荷・応答性を検討する重要な条件になる。

**今すぐ変更するより、まず現在の安定設定で負荷と音切れを測定する**のが安全である。

## 5. おすすめの開発順序

1. **レスポンシブ GUI と現行再生系の安定化**
2. **設定モデル・DSP 適用経路・ゲイン管理の整理**
3. **ヘッドホン機種補正＋簡易音色調整**
4. **遅延と周波数特性を持つクロスフィード**
5. **スタジオ／ホールの空間プリセットと距離感調節**
6. **スピーカー用クロストークキャンセルを実験機能として追加**

各段階で YAML の検証だけでなく、以下まで確認する方針がよい。

- 片チャンネル入力による経路確認
- 周波数応答・ピーク確認
- 設定切替時の音切れの確認
- 音量をそろえた試聴

## 7. 方針更新：リスニングルーム特化と Android 連携

- 追記日: 2026-09-18
- 背景: Android 側の既存資産と、Linux 側をスピーカー聴取に重点化したいというユーザーの意向。
- 本章の位置づけ: 第1～6章の技術的な評価を基礎に、製品の役割分担と開発優先順位を更新する。新機能の実装完了を示すものではない。

### 7.1 前提と役割分担

ユーザーから共有された Android DSP ステーションの実装状況は次のとおり。

- 約2800機種のヘッドホン／イヤホンデータを保有する。
- ハーマンカーブへの近似補正を実装済み。
- A機種をB機種の特性に近づける再キャリブレーションも実装済み。

これらはユーザー提供情報であり、Android のコード、測定データ、フィルター生成方式、エクスポート仕様は本作業では未確認である。

| 項目 | Android DSP ステーション | Linux 本システム |
|---|---|---|
| 主な聴取環境 | モバイル、ヘッドホン／イヤホン | 固定設置のスピーカー、リスニングルーム |
| 主な機能 | 機種補正、目標音色、A→B 特性近似 | 仮想空間、初期反射・残響、クロストークキャンセル |
| 連携時の役割 | 操作端末、プロファイル共有、将来の計測補助 | 音源再生、DSP 実行、適用状態の管理 |

**Linux にヘッドホン機能を丸ごと移植することを優先せず、Android の資産を必要な範囲で共有する。** 外出先は Android、室内は Linux と役割を分けることで、重複開発を抑えながら発展できる。

### 7.2 A→B 変換技術の再利用範囲と限界

既存エンジンが周波数応答の差分を近似する方式なら、次の技術は再利用候補になる。

- 測定曲線・目標曲線の読み込みと管理
- 周波数応答の平滑化、PEQ フィッティング
- ブースト量の制限、プリアンプの算出
- プロファイルの比較・保存・表示

ただし、**ヘッドホンの音色変換と、部屋・スピーカーを含む音場の変換は同一の問題ではない。** 共通なのは「現状と目標の差を扱う」という発想と一部の信号処理である。

部屋には反射の方向・到達時間、残響の減衰、スピーカーの指向性、聴取位置による変化がある。周波数特性だけを合わせても、別のスタジオの音場は再現できない。また、深い打ち消しによるディップを大きく持ち上げる補正は避ける必要がある。

クロストークキャンセルは左右スピーカーから左右耳への伝達を扱う多経路の問題であり、単一の A→B EQ をそのまま転用できない。幾何モデル・耳への伝達モデル、帯域や補正量の制限、フィルターの安定性と位置ずれへの検証が別途必要になる。

**既存エンジンの移植可能性は高い部分があるが、「そのまま部屋変換エンジンになる」とは断定しない。** 実測を前提にしない当面の路線では、補正エンジンより空間モデルと合成 IR の設計を優先する。

### 7.3 Linux 側の中心機能：スピーカーによる環境疑似体験

まず、次の2モードを分離する。

| モード | 目的 | 初期版の範囲 |
|---|---|---|
| 空間演出 | スタジオ・小ホールなどの響きや奥行きを付加する | 合成 IR、控えめな初期反射、残響量、距離感プリセット |
| クロストークキャンセル | 固定リスニング位置で左右耳への不要な回り込みを減らす | 配置を入力するモデルベースの帯域限定・補正量制限付き実験 |

空間演出では「実際のスピーカー配置」と「仮想会場の大きさ・距離感」を別のパラメータにする。仮想距離を変えても、クロストークキャンセルが前提とする実配置まで変わらないようにする。

通常のステレオ録音と、耳元の信号を想定したバイノーラル音源では、クロストークキャンセルの目的や聴感が異なる。音源種別を区別し、通常ステレオへの効果を一律に音質改善と見なさない。

2本のスピーカーでも空間感の演出は可能だが、部屋全体を別会場へ置き換えることや、複数の聴取位置で同じ音場を保証することはできない。後方・側方からの包囲感を重視するなら、将来のマルチチャンネル化も検討対象になる。その場合は現在の2ch出力前提を拡張し、共通クロックで動く多出力機器を検討する。

### 7.4 Android 連携の発展段階

#### A. リモコン・シーン操作：最初の連携として推奨

既存の REST API と WebSocket を利用し、Android から再生、音量、空間プリセット、適用結果の確認を行う。まずレスポンシブ Web UI を携帯で使い、専用アプリへの統合はその後でもよい。

音声をスマホ経由にする必要はない。音声処理は Linux 内で完結させ、スマホは制御と表示を担当する。

```text
Android／モバイル Web UI
  ⇅ 設定・プリセット・再生状態（LAN）
Linux API／設定管理
  → DSP 構成生成・検証・適用
  → CamillaDSP → DAC → スピーカー
```

既存 API があることと、安全な外部端末連携が完成していることは別である。接続先設定、ペアリング／認証、通信保護、音量上限、複数端末からの変更競合、切断後の状態復旧を設計する。CamillaDSP の制御ポートをスマホへ直接公開せず、Linux API を窓口にする。

#### B. プロファイル／プリセットの共通形式

共通 JSON 等で次を表現できるようにする。

- スキーマのバージョン、プロファイル ID、用途、出典・利用条件
- PEQ の種類、周波数、Q または帯域幅の定義、ゲイン、プリアンプ
- 対象機器、目標曲線、補正と音色調整の区別
- 空間シーンと、そのシーンを実現するための必要機能

同じデータを読み込めても同じ音になるとは限らない。フィルターの定義、サンプルレート、ゲイン規約をそろえ、各エンジンで応答を比較する必要がある。ヘッドホン補正をスピーカーへ誤適用しない用途チェックも必要になる。

API の追加だけでなく、検証、保存、互換性、DSP 生成、UI、テストを含む機能として見積もる。初期段階では全2800機種の移植より、少数のプロファイルで相互運用を検証する。

#### C. 設置ガイド・測定補助

スマホはスピーカー配置の入力、設置写真、リスニング位置の記録、測定手順の案内などに利用できる。まず巻尺等で確認した配置を入力する方式なら、実測音響補正を導入せずに開始できる。

マイクを使う場合は、次の限界を区別する。

- 独立した Linux 再生と Android 録音では、時刻原点・入出力遅延・クロック差が不明なため、録音の到達時刻だけから絶対距離を求めることはできない。
- 相対到達時間や相対レベルは、適切な基準信号、録音条件、AGC・ノイズ抑制の制御を検証したうえで利用を検討する。
- 未校正マイクの周波数応答・感度、端末の自動処理は測定結果に影響する。「一般のスマホで十分な精度」とは事前に保証できない。
- リスニング位置中央の単一マイク測定だけでは、クロストークキャンセルに必要な左右耳への4経路を直接取得できない。

将来の精密なルーム測定には校正済みマイクが有用だが、それだけで耳間伝達の測定が完成するわけではない。耳位置に対応した計測配置やモデルと、タイミング基準も必要になる。測定機能は将来の任意拡張とし、環境疑似体験の必須条件にはしない。

#### D. メディア連携

確認した既存 UPnP ルーターは、Soundgenic／Asset 等の外部サーバーを参照するブラウズ・検索機能である。**Linux 自身が UPnP メディアサーバーや汎用レンダラーとして公開済みであるとは確認していない。**

Android から既存 Linux API を操作して音源を選び、Linux で再生する方式が初期案として現実的。スマホ内の音源を Linux で再生する場合は、音源の提供方法、到達可能な URI、認証、対応形式、Android のバックグラウンド動作制約を別途設計する。

Bluetooth の既存経路は主に Linux から機器への出力であり、Android からの音声受信機能が完成していることを意味しない。

#### E. ヘッドトラッキング：中長期の研究項目

固定したスマホのカメラによる頭部位置推定などは候補になるが、手に持つスマホの姿勢センサーだけでは頭部位置・向きを取得できない。

位置精度に加え、撮影・推定・通信・音声出力までの総遅延と、フィルター切替時の連続性を検証する必要がある。現在の YAML リロードを高頻度に繰り返すだけで実現できるとは考えない。

Android と Linux の同期音声再生も不可能ではないが、専用の時刻同期・バッファ管理・クロック補正が必要。初期連携は非リアルタイムの設定・状態・プロファイル共有を中心とする。

### 7.5 Bluetooth に関する説明の訂正

前の会話での「Bluetooth はエフェクト OFF という制約がある」という一律の説明は訂正する。

`/home/tysbox/HQ_Linux_Music_Player/backend/dsp/state_manager.py` の確認範囲では、**Bluetooth で Pure モードを要求した場合**に DSP パススルーへ変換し、エフェクトを無効化している。通常の DSP モードまで一律に禁止する実装ではない。

ビットパーフェクト性と DSP 適用可否は別問題である。ただし、精密な左右の位相関係を扱う初期検証では、独立した無線出力を組み合わせるより、左右を共通クロックで出力する有線 DAC を基準にするほうが条件を管理しやすい。

### 7.6 更新後の開発優先順位

1. **レスポンシブ GUI・既存再生系の安定化** — スマホからの基本操作もここで確認する。
2. **DSP 基盤の整理** — 設定モデル、適用確認、ゲイン管理、処理段の分離を整える。
3. **スピーカー用空間演出の初期版** — 合成 IR によるスタジオ／小ホール、初期反射、残響量、距離感を検証する。
4. **Android からのシーン操作・共通形式の小規模検証** — リモコンを先行し、全機種 DB 移植は後回しにする。
5. **固定位置向けクロストークキャンセルの試作** — 実配置と音源種別を明確にし、帯域・補正量を制限して検証する。
6. **必要性に応じた測定補助・位置追従・マルチチャンネル化** — 初期版の結果と利用機器を踏まえて選択する。

**Linux は「Android の据え置きコピー」ではなく、「スピーカーで空間を楽しむ再生拠点」とする。Android はその操作・共有・将来の計測補助を担う。** この分担には十分な発展性があるが、部屋の完全再現や無測定での高精度な打ち消しは保証しない。
