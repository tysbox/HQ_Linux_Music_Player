## 1. 点検の結論

本コミットは新 GUI の追加だけでなく、旧 GUI・旧サービス構成の撤去も兼ねている。主要ソースと systemd 設定は残され、Python 構文検証、共通コアの単体テスト、Next.js 本番ビルドは成功した。

ただし移行後の整合性には問題がある。優先度の高い事項は次のとおり。

1. 旧 3000/3001/3002・8000/8001 を前提とする E2E テストが残っている。
2. MPD client を lock 外で操作する経路がある。
3. health check の `async def` 内で同期ソケット I/O を行う。
4. CamillaClient の切断が例外時に保証されない。
5. メタキャッシュが全件を毎回、非 atomic に書き戻す。
6. アート cache が core と router に二重実装されている。
7. 新 GUI 用の統合 E2E がない。
8. WebSocket と REST polling が同じ状態取得を重複している。
9. version、設定値、CORS、API client の定義が分散している。
10. ESLint script が実行不能である。
11. GUI asset 更新処理に、中断耐性の低い destructive 操作がある。

**system 破壊リスクが高く、優先度.matcher Panther の低い項目**（systemd 一括適用・再起動、live asset 更新、CamillaDSP/ALSA/MPD 実操作）は通常修正手順から除外し、第 6 章で別途管理する。

### 2.1 通常修正対象（P1〜P2）

- `systemctl restart` / `daemon-reload` による実サービス切替

これらは構文エラーや設定不整合より、返却途中の障害・無音・再生停止・復旧権限依存のリスクが高い。実環境 touch は staging で確認し、operator の別承認後に release runbook として実施する。

## 3. 点検結果と修正方針

### P1-1: 旧構成を前提とする E2E テスト

**対象**

- `tests/e2e/test_hq_api_compat.py:24-26, 88-101`
- `tests/e2e/test_hq_api_stress.py:24-25, 83-94`

旧 `8000`、`8001`、`3002` の alive を前提にしているが、現行 README/HANDOVER は旧ポートを使用しないと明記している。

**修正**: 現行 8002/3003 の smoke/integration test を独立させる。旧比較は通常 CI から除外するか `legacy-compat` profile に移し、fixture/mock 化する。

**受入基準**: 旧サービスが起動していない状態でも現行 test が通る。通常 test が 3002/8000/8001 へ HTTP request しない。

### P1-2: MPD client の lock 外利用

**対象**: `hqmplayer_core/mpd/client.py:123-137`, `hq_api/main.py:148-151`。

`get_client()` は lock 内で client を返すが、health check がその client を lock 外で `ping()` する。

**修正**: MPD 公開操作を `mpd_connection()` など lock 管理済み context に統一する。利用箇所を全件検索し、raw client 直接利用を禁止するか read-only probe 専用にする。

**受入基準**: 全 MPD command が同一 lock policy を通り、health と通常 API の同時実行で protocol が混線しない。

### P1-3: health check 内の同期 I/O

**対象**: `hq_api/main.py:141-173`。

`async def health()` 内で `socket.create_connection()` を直接実行している。既定 0.5 秒でもイベントループをブロックする。

**修正**: probe を `asyncio.to_thread()` へ移すか async client 化する。timeout の上下限を定義し、MPD と DSP の timeout を分離する。

**受入基準**: DSP 停止時も無関係な非同期 request をブロックせず、CamillaDSP を実変更しない mock test で検証する。

### P1-4: CamillaClient の切断保証

**対象**: `hq_api/routers/dsp.py:117-134`, `dsp_write.py:97-118`, `dsp_apply.py:190-200`。

接続後の状態取得や reload が例外になっても `disconnect()` が保証されない。

**修正**: client lifecycle を context manager に集約し、connect 後の全例外で finally disconnect する。

**受入基準**: mock client で状態取得、reload、volume 設定が例外になっても disconnect が呼ばれる。

### P1-5: メタキャッシュの非 atomic・全件書き込み

**対象**: `hqmplayer_core/meta/cache.py:82-88, 95-116`。

`store()` ごとに全 JSON を通常 open/write する。crash、disk full、並行 request で壊れた cache を作り得る。

**修正**: temporary file + `os.replace()`、lock または単一 writer、debounce/batch、schema/version、壊れた JSON の安全退避を導入する。import 時の `_load()` は lifecycle 化を検討する。

**受入基準**: simulated exception 後も旧 cache が読め、並行 store でも JSON が壊れず、load 失敗が API 全体を落とさない。

### P1-6: アート cache の二重実装

**対象**: `hqmplayer_core/art/resolver.py` と `hq_api/routers/dsp_readonly.py:31-69`。

router 側に iTunes art cache、core 側に art resolver が存在し、TTL と責務が分散している。

**修正**: cache policy を `hqmplayer_core/art` に集約し、既存 cache の移行を一時的に用意する。router は `resolve_art()` と response conversion だけを担当する。

**受入基準**: アート優先順位と cache policy が一つに定義され、別 package からも同じ cache policy を利用できる。

### P2-1: 新 GUI 統合 E2E の欠落

旧 `unified-shell/e2e/` は削除されたが、新 GUI 用の同等 test がない。

**追加範囲**: 3003 `/`、8002 `/` と `/health`、library read API、`/ws/now_playing` 接続、queue の read/write、3003 HTML が参照する主要 JS/CSS asset の取得。音楽再生、CamillaDSP restart、実音量変更は初回 test から除外する。

**受入基準**: 3003 と 8002 の接続、UI asset、主要 API、WebSocket の疎通を test で確認できる。

### P2-2: version 不整合

`phase3a`、`phase3b`、`0.1.0` が複数箇所に混在する。

**修正**: release version と API version を定義し、`hq_api.__version__`、FastAPI metadata、root、WebSocket ready から参照する。GUI package version は GUI revision と分離する。

**受入基準**: OpenAPI、root、package、document の version の意味が文書化され、意図しない不一致がない。

### P2-3: WebSocket と REST polling の重複

`usePlaybackStatus.ts` は WebSocket と 2 秒ごとの `/api/playback/status` polling の両方を使う。position は UI 側で補間している。

**修正**: `/ws/all` に random/repeat/position を含められるか確認し、WebSocket を正式 stream、REST を初期接続・fallback に限定する。再接続 backoff と複数タブの扱いを定義する。

**受入基準**: 通常の playing 状態で不要な status request が減り、最終更新経路と fallback が明確である。

### P2-4: 設定値の分散

MPD、CamillaDSP、API port、CORS の default が複数ファイルに hardcode されている。`ALLOWED_ORIGINS` 設定時は `HQ_GUI_ORIGINS` が追加されない。

**修正**: 設定 loader を新設し、parse/validation/default を一箇所に集める。CORS は「完全置換」または「追加」を明示し、README と実装を一致させる。

**受入基準**: 同一 env が `hq_api`、`hqmplayer_core`、router で異なる値にならない。不正値は起動時に明確な error になる。

---

### P2-5: ESLint script が実行不能

`new-gui/package.json` に lint script がある一方、ESLint 9 の `eslint.config.*` がない。

**修正**: `eslint-config-next` の version に合わせて `new-gui/eslint.config.mjs` を追加し、warning/error policy を決めて `npm run lint` を CI の必須 job にする。

**受入基準**: lint が config missing で終了せず、build も成功する。

### P2-6: API client の重複

`new-gui/src/lib/api.ts` と `upnpApi.ts` が同じ API base URL と fetch policy を個別に組み立てている。

**修正**: base URL、timeout、JSON error handling を共通 HTTP module へ分離する。localhost/127.0.0.1 の直接 hardcode を検査する。

**受入基準**: API host 決定箇所が一つになり、3003 の hostname から 8002 への接続が開発・本番・LAN で一貫する。

### P2-7: `check_sync.sh` の検査範囲不足

現在の grep は限定文字列検出で、設定値、IP アドレス、env 間接参照を完全には検出しない。

**修正**: 検査 directory を自動決定し、localhost/127.0.0.1/0.0.0.0/env literal を検査する。検査対象が存在しない場合は「未検出」と区別する。

### P2-8: GUI asset 更新の安全性

`new-gui/audiophile-new-gui.service` と `scripts/deploy_gui.sh` は `rm -rf` と copy を含む。途中終了で static/public が失われる可能性がある。

**本提案での扱い**: live 更新・service restart は除外する。通常工程では build output の静的検査だけを行い、release directory を分離した安全な deploy 設計を別途作成する。

## 6. 高リスク・低優先度項目の扱い

| 項目 | 除外理由 | 将来の方向性 |
|---|---|---|
| live systemd 一括配置・再起動 | 複数サービスが同時に落ちる | staging → verify → 1サービスずつ適用 |
| `.next/standalone` の live 置換 | asset 消失、途中失敗で GUI 破損 | release directory と current 参照の分離 |
| CamillaDSP/ALSA 実変更 | 再生停止・無音・競合 | mock/staging を先に整備 |
| 実機 queue/volume | 再生状態を変更 | read-only test を基本にする |
| `git reset --hard` | 未保存作業消失 | patch/backup artifact rollback |
| low-priority の命名・default 整理 | 単独では障害直結しない | 上位 task 後に opportunity として整理 |

これらを安全化せず実行するのではなく、まず dry-run/staging/mock 化し、実環境変更の承認を別途取得する。

## 8. 最終推奨順序

1. 旧 test 契約の整理
2. MPD lock 統一
3. health 非同期化
4. CamillaClient 切断保証
5. cache atomic 化
6. 新 GUI の lint/build/E2E smoke
7. art cache 集約
8. WebSocket 状態統合
9. version 統一
10. 設定 loader・CORS policy 集約
11. 共通 HTTP client 化
12. 文書・unit template・check script 同期
13. staging unit verify
14. 実環境 service apply（別途承認）
15. 再生・音声経路・rollback の受入確認

この順序なら backend の安全化、test 契約、GUI、cache、文書を小さく検証しながら進められる。live な音声・systemd 変更を最後に分離することで、システム全体の破壊リスクを最小化する。
